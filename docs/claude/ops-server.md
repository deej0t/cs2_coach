- **`cs2.deej0t.eu`** points at the home IP (config `server_address`, shown on `/server` with a steam://connect link). Kept current by the Unraid container `cloudflare-ddns` (`favonia/cloudflare-ddns:1`, template `my-cloudflare-ddns.xml`, every 5 min, also manages the apex `deej0t.eu`). Token (DNS edit for deej0t.eu only) in `/mnt/user/appdata/cloudflare-ddns/token`, never in the repo. **`PROXIED` must stay false**: Cloudflare's proxy carries no game traffic. The home IP does change: `www.deej0t.eu` still pointed at an old one (91.184.172.121) on 2026-10-30. `health.check_game_server()` compares the name with the public IP (Cloudflare trace) and queries A2S_INFO through it - the path players use; NAT hairpin on the router makes that work from the LAN.
- The *previous* server `cs2-practice` (`joedwards32/cs2`, removed 2026-10-01) never worked: its mount was root-owned, the container ran as 1000:1000, so SteamCMD installed CS2 into the container's *writable layer* - 69 GB inside `docker.img`, restarted 1139 times. Any game-server container needs a bind mount writable by its UID.
- **Measuring a container's disk use means its writable layer too** (`docker ps -a --size`), not just its bind mounts. The mount above read 0 bytes while the container held 73.6 GB.
- Space freed inside `docker.img` only returns to the cache after `fstrim /var/lib/docker` (the loop device supports discard). Unraid's nightly TRIM (02:00) does include `/var/lib/docker`; the user also runs an extra `docker-img-trim` job. Nightly container auto-updates (`ca.update.applications`, 00:00) write and free ~70 GB/day inside `docker.img`, so it grows between trims — that is expected, not a leak.
- **`RUN git clone` in the Dockerfile used to be cached**: a rebuild on 2026-10-16 silently produced two-commits-old code. An `ADD` of the GitHub branch ref now busts the cache; still verify with `docker run --rm --entrypoint sh cs2-coach:latest -c "cd /app && git log --oneline -1"`.
- **`/app` lives in the container, not on a volume.** Code arrives by `git reset --hard` in `docker-update.sh`, but a *recreated* container starts from the image's `/app` again — i.e. from whenever the image was built. Recreate only after rebuilding the image (`docker build -t cs2-coach:latest https://github.com/deej0t/cs2_coach.git#main`), or the server silently runs old code.
- **The entrypoint must run from `/app`, never from a copy baked into the image.** Until 2026-10-13 the Dockerfile copied it to `/usr/local/bin`; the server's image from 2026-08-30 had no update loop, so **auto-update never ran on the server** — every update until then was triggered by hand. Symptoms were invisible: last fetch 293 h old, no "Auto-Update aktiv" in the log, and `qrcode` missing (QR login broken). The entrypoint now installs missing requirements at start and runs the first update check 5 min after start (not earlier: `docker-update.sh` HUPs PID 1, which is only gunicorn after `exec`).
- **"healthy" is not "reachable".** The healthcheck calls `localhost:5000` *inside* the container and passes even when the published port is wrong. The server's Portainer stack (`/mnt/user/appdata/portainer/compose/10/docker-compose.yml`, which differs from the repo's) had `"5001:5001"`; recreating the container on 2026-10-13 made the WebUI unreachable for a day (the Cloudflare tunnel `cs2-coach.deej0t.eu` → `192.168.188.71:5001` got "connection refused"). It must be `"5001:5000"`. After every recreate, check from outside: `curl -s -o /dev/null -w "%{http_code}" https://cs2-coach.deej0t.eu/` → `302` (login redirect).
- **Demos without analysis** (`health.check_unanalyzed`, since 2026-11-14): a `.dem` in the demo folder without an export is OK for `PENDING_GRACE_H` (3 h - sync every 2 h, then batch), older = WARN (Discord on state change + a yellow band on the start page). On 2026-11-12 two demos failed in demoparser2 and the matches were missing for a day without any hint.
- **System status** (`health.py`, `/status`, `cs2-coach health [--notify]`): public URL reachable from outside (`public_url`), last update check age and HEAD vs origin, Steam session, disk usage of `/data` (= the cache) and the demo folder, demos findable for every export, exports needing re-analysis. The container runs `health --notify` in its **own** loop (every 30 min, `CS2COACH_HEALTH_INTERVAL`, first run 10 min after start) — not inside the update loop, or a hung update loop could never report itself. Discord (`health_webhook`, else `discord_webhook`) only gets **state changes**; the state file `.health_state.json` next to the config is written only after a successful send, so a missing webhook or failed post is retried.
- **Host load + SMART** (`health.check_host()`): `docker/unraid/host-status.sh` (cron `*/5`, `/boot/config/plugins/dynamix/host-status.cron`) writes `host_status.json` next to the config - load, per-disk utilisation (iostat over 5 s), top-5 containers by CPU, SMART realloc/pending/uncorrectable (standby disks are not woken). The container cannot see any of that itself. Load15 > cores = warn, > 4x cores = fail, with the busy disks and containers in the message; file older than 20 min = warn. SMART: realloc above the first value seen per disk (`.host_smart_baseline.json`, sdb started at 8) = warn, pending/uncorrectable > 0 = fail. **Cron must call scripts on /boot with `bash`** (FAT, no exec bit): host-status ran `exit 126` from install (11-03) until 11-06, so `host_status.json` was stale (permanent "Server-Last=warn") and the 11-06 stall (04:15-07:20, cron runs 5-7 min late, winbindd requests 87 s) left no measurements. Since then each run also appends one line to `host_status.log` (last 1000 = ~3.5 days) and logs `host-status: Ueberlast ...` (top CPU + D-state processes) to syslog when load5 > 2x cores. **2026-11-03 "server hangs" was load > 200**: sabnzbd downloaded and unpacked directly on the parity array (share `data` without cache); its temp folder now lives on `ssdcache` (`/incomplete` -> `/mnt/ssdcache/sabnzbd-incomplete`), next download peaked at load 5.
- **External alarm = heartbeat, not polling.** `health --notify` (every 30 min) posts the check results to `heartbeat_url` (healthchecks.io); any `fail` goes to `<url>/fail` for an immediate alert, warnings do not alert. No ping (server, container or internet down) -> healthchecks.io alerts. Polling from outside does **not** work: the GitHub Actions check (`.github/workflows/uptime.yml`, now manual-only) got **HTTP 403 from Cloudflare's bot protection** on 2026-10-17 while the server was fine, and GitHub ran only 1 of 8 scheduled runs in 4 h. GitHub's failure e-mail itself works (`alarmtest.yml`, manual). The ping URL is in the server's config.yaml only - anyone holding it can send pings, keep it out of the repo.
- **UPS** (`check_ups`, config `ups_host`): queries the host's NUT daemon over TCP 3493 (`LIST VAR ups`, no login needed; reachable from the container via the LAN IP or 172.17.0.1). `ERR DATA-STALE` = daemon up but USB link to the UPS gone - that was the state for three days from 2026-10-14 (31,000 USB reconnects; changing the port did not help, restarting NUT did). OB/LB = on battery -> fail. Shutdown timer is 60 s (`nut-dw.cfg`, was 240 s at a measured runtime of 238 s). **2026-10-25: the breaker tripped at 14:57 while the USB link had been dead since 08:32** - the UPS carried the load, NUT was blind, the server never shut down and died with the battery (log ends mid "Data stale"; it powered on by itself when mains returned). The health alert had fired at 08:45. Fix: `docker/unraid/nut-waechter.sh` (cron every minute since 2026-11-08, `/boot/config/plugins/dynamix/nut-waechter.cron`) restarts NUT after 5 min without data (60 s in the first 15 min after boot: on 2026-11-08 the driver found no UPS at boot, `No matching HID UPS found`, and NUT was blind for 6 min) (`rc.nut stop` + `start`, a second `start` if needed - NUT came back only on the second start both on 2026-10-16 and in the 2026-10-25 test), at most every 15 min, and reports via Unraid notify. Tested by stopping only the driver (`upsdrvctl -u root stop`). Only **one** UPS daemon: the user had enabled Unraid's `apcupsd` as well, which could never reach the UPS (NUT holds it) - disabled again (`dynamix.apcupsd.cfg` SERVICE="disable"). **Probably not the cable**: 608 disconnects with zero USB protocol errors (no `error -71`/descriptor failures) in a metronomic ~11 s rhythm point to the UPS resetting its own USB interface - a known CyberPower + NUT issue; the driver itself logs "You may want to set 'pollonly' flag on CPS devices". Since 2026-10-25 `pollonly` is set on **line 9** of `ups.conf` (`/etc/nut/` and the persisted copy in `/boot/config/plugins/nut-dw/ups/`): in non-manual mode the plugin only rewrites lines 1-8 (name, driver, port, SNMP, debug), so line 9+ survives GUI saves and reboots. Check with `upsc ups driver.flag.pollonly`. If watchdog restarts continue anyway: cable, then the UPS itself. **2026-11-08 ~11:20 the breaker tripped and the server died instantly with NUT connected and healthy** - not one `on battery` line, `unclean shutdown detected` at boot: the UPS did not carry the load at all. Suspect the battery (deep discharge to empty on 10-25); check the outlet, test the UPS with a lamp, replace the battery.
- **Fan control** (2026-11-06, `docker/unraid/luefter.sh`, cron `*/1` in `/boot/config/plugins/dynamix/luefter.cron`, with `bash`): the board's sensors (`asus_wmi_sensors`) are read-only; the Unraid plugin "IT87 Drivers" (ich777) loads `it87`, which finds the **IT8665E** -> hwmon `it8665` (index changes, find by name). pwm1 = CPU fan (chip auto, enable 2, left alone), pwm2/pwm3 = chassis fans (were enable 0 = 100 % permanently), pwm4 = chipset/HAMP fan (left alone), pwm5/6 unused; the fan-extension-card fans (EXT 1-3) are not on this chip. The script drives pwm2/3 from the hottest of HDD (disks.ini, 36->45 C, sleeping disks do not count), NVMe (50->65 C) and CPU Tdie (60->80 C), minimum 35 % (pwm 89 = 928/822 rpm; temps rose ~1 C at idle), 100 % on any missing reading or a fan at 0 rpm; logs jumps >= 15 % (`luefter`). The Dynamix Auto Fan plugin is installed but unconfigured - never enable both.
- **Never create anything under `/mnt/user` from a cron script without `mountpoint -q /mnt/user`.** Cron runs during boot before the array starts; if emhttpd finds directories under `/mnt/user` it logs `malloc_share_locations ... getxattr: Operation not supported` and **does not mount shfs at all** - every container then runs on empty directories in RAM (rootfs). 2026-11-12: `server-demos.sh` (`mkdir -p /mnt/user/appdata/...`, installed that afternoon) did this on two boots (16:29 and 19:18, first boots with Unraid 7.4.0 after an unexplained outage ~15:45); coach without config, CS2 commands unanswered. Fixed with the guard in `server-demos.sh` and `host-status.sh`. The user's own `cache-wacht.sh` (`mkdir -p /mnt/user/data/shorts/status`, 02:45/07:45/19:45) has the same risk - reported, not touched. Also: a plugin installer (`unraid-connections`) stopped rsyslogd at 16:31 without restarting it - syslog was empty for 3 h.
- **Memory: no swap, 32 GB.** 2026-11-04 03:08 a global OOM killed `Plex Transcoder` at 17 GB RSS (night maintenance); 11-02 tunarr/meilisearch hit their own cgroup limit. Plex template `my-plex.xml` now has `--memory=8g` (backup `my-plex.xml.bak-20261106`, needs "Apply") so Plex cannot starve the host.
- **Server hardware: Threadripper 1920X (Zen 1) on ASUS ROG Zenith Extreme, 4x8 GB DDR4.** 2026-11-01 the server stalled from 00:20 (vnstatd needed 340 s, later 2834 s to write its RAM-backed db) and hung completely - log ends 07:11, no SSH, no console login. Not the parity check (starts 09:00, schedule runs 9-14 daily), not the disks (cache scrub at 00:00 clean, SMART clean). Changed in the BIOS: RAM from 3200 (D.O.C.P., above Zen 1's 2666 spec) to Auto = 2133, and Power Supply Idle Control = Typical Current Idle (known Zen 1 idle freeze). If it hangs again: Global C-state Control off, then Memtest. The syslog is mirrored to flash (`/boot/logs/syslog-previous` holds the previous boot).
- **Every Docker start re-inflates docker.img to its full 250 GB.** Unraid's `/usr/local/sbin/mount_image` runs `fallocate -l 250G docker.img` on each start of the Docker service (boot, OS update, Docker off/on), which re-allocates every hole TRIM had punched: 93 GB used, 249 GB on disk, cache below the appdata floor, containers cannot create files. Proven 2026-10-17 after the 7.3.3 update: 249 GB with only 1.1 GB written since boot. (The 2026-10-16 case was the reboot after the crash, not the crash - an earlier note blamed the crash.) Fix: `docker/unraid/docker-img-autotrim.sh`, installed to `/boot/config/custom/` with a `*/10` cron in `/boot/config/plugins/dynamix/docker-img-autotrim.cron` (activate with `update_cron`); it trims only when the file exceeds usage by >20 GB and logs to syslog tag `docker-img-autotrim`. The user's own `cache-wacht.sh` (02:45/07:45/19:45, Shorts project) stays untouched. Container `onyx` holds 22 GB in its writable layer (not ours - reported, not touched).
- **A cache with free space can still refuse writes.** Unraid's share setting "Minimum free space" (appdata: `shareFloor=48800000` KB = 48.8 GB in `/boot/config/shares/appdata.cfg`) makes shfs answer ENOSPC for *new* files once the pool drops below it - on 2026-10-16 at 32 GB free (94 %) every container got "No space left on device". `check_writable()` therefore actually creates a file next to the config. The space was inside `docker.img` (249 GB on disk, 93 GB used): `fstrim -v /var/lib/docker` freed 158 GB.
- **Entrypoint changes only take effect after a container restart** — the running shell already forked its loops. And after a recreate the entrypoint comes from the *image's* `/app`, so rebuild the image too.
- **Never set `entrypoint:` in a compose/stack file.** Compose then drops the image's `CMD`, `exec "$@"` gets nothing, the container exits 0 and restart-loops. Happened on the server on 2026-10-13 (about two minutes of downtime). Old images must be rebuilt instead.
- Checking CR line endings from Git Bash: `grep -c $'\r'` matches every line there (it reported 75 of 75). Count bytes instead: `git cat-file -p HEAD:file | tr -cd '\r' | wc -c`.
- **Network jitter on the warmup server** (2026-11-01): the player connected via the public IP (log `chan->addr=91.184.163.134`) = NAT hairpin through the router - at home use `connect 192.168.188.71`. Other suspects that day: parity check running, CPU governor `ondemand`, StirlingPDF and social-hub containers at 30-40 % CPU each.
